# 作業後のメモの保存

[English](automatic-capture.md) | 日本語 | [説明書一覧](README.ja.md)

作業が終わったら、次にも役立つことを、人が確認できるメモとして保存できます。コマンドの出力で `capture` と表示されることがありますが、会話を丸ごと保存する機能ではありません。

## 保存の流れ

```text
作業を終えて結果を確認する
  -> 次にも役立つ内容か判断する
  -> 必要な項目だけの短い要約を作る
  -> 秘密情報や会話原文のような入力を拒否する
  -> 重複と、使用中の判断との食い違いを確認する
  -> 確認待ちのメモを保存するか、別の作業で得た根拠を追加する
  -> 未確認であることを示したまま、後の検索で見つける
  -> 人が内容を確認する
```

書き込むのは確認待ちメモのフォルダだけです。確認済みのメモは編集しません。

## 保存すると役立つもの

次の作業の判断や進め方を変えそうな内容だけを残します。

- プロジェクトについて確認できた事実。
- 利用者の好みや、明示された制約。
- 失敗した方法、確認できた原因、検証した直し方。
- 確認手順まで含む、繰り返し使える作業方法。
- 判断の提案、その理由、適用する条件。

作業が完了したという理由だけでは保存しません。通常は、次のような内容を省きます。

- 誤字の修正。
- 単純な名前の変更。
- 結果が明らかな1行の変更。
- 見た目だけの整形。
- 新しい発見のないビルドやテストの実行。
- 返事、進捗報告、変更したファイルの一覧。

失敗した作業でも、失敗内容と根拠が明確なら次に役立つメモになります。確認できていない推測は、未確認の観察として明記するか、保存しません。

## JSONで短い要約を渡す

`brain learn-extract` は、項目を決めた1つのJSONを受け取ります。会話原文やツールの全記録は受け取りません。

```json
{
  "project": "sample-weather-cli",
  "task_type": "debugging",
  "task": "Prevent stale synthetic weather records from being displayed",
  "outcome": "success",
  "new_findings": [
    "Cached records need an explicit capture time before age can be validated."
  ],
  "user_corrections": [],
  "failed_approaches": [
    "Checking only that the cache file existed accepted stale records."
  ],
  "successful_approaches": [
    "Compare captured_at with the configured maximum age and test with a fixed clock."
  ],
  "reusable_knowledge": []
}
```

これは動作確認用の架空データなので、項目名や値は英語のまま掲載しています。実際に使うときは、値を自分の作業の短い要約に置き換えます。

JSONの `project` と `task_type` はコマンドで指定したものと一致させます。`outcome` は `success`、`partial`、`failure`、`cancelled` のいずれかです。各リストには調べてわかったことを書き、ターミナルの出力をコピーしません。

`reusable_knowledge` は省略できます。指定する場合、各項目の種類は次の6つです。

- `fact`
- `preference`
- `constraint`
- `lesson`
- `procedure`
- `decision`

自動保存で扱うのは、この6種類だけです。`project-rule`、`principle`、`protocol`、`skill` などは、人が作成して確認します。メモを保存しただけで、今後のAIが従う指示にはなりません。

どの登録済みプロジェクトにも一意に対応しない内容を、別のプロジェクトのメモとして保存しないでください。複数のプロジェクトへ内容を変えずに使える知識だけを、共通の範囲に保存します。

## 保存されるもの

新しいメモは `inbox/candidates/` に置きます。各項目を見ても、未確認のメモだと分かります。

```yaml
candidate: true
authority: candidate
review_status: pending
status: pending
evidence_count: 1
```

メモには、情報の出所、判明している場合は対象プロジェクト、実在するメモへのリンクを記録します。確認待ちのメモへリンクしても、どちらかが確認済みになるわけではありません。このフォルダのメモは、通常のグラフの件数から除外されます。

残す内容がなければ、保存せず終了します。これはエラーではありません。

## 重複を避け、別の作業で確認できたことを数える

書き込む前に、同じプロジェクトにある同種のメモ、またはプロジェクト共通の同種メモと比べます。

- 同じ内容のメモをもう1つ作らない。
- 同じ作業要約を再送しても根拠の数を増やさない。
- 別の作業で同じ内容を確認できた場合は、`evidence_count` と `last_observed` を更新できる。
- 根拠が増えても、自動で確認済みにはしない。出力ではこの更新を `reinforced` と呼ぶことがある。

同じ知識かを識別するために内容のfingerprintを使い、別の作業による根拠かを区別するためにobservation signatureを使います。どちらも利用者のIDやセッションIDではありません。

## 使用中の判断と食い違う可能性がある場合

新しいメモが現在使っている判断と食い違う可能性がある場合、`conflicts_with` という関係と警告を記録します。文章の意味が本当に矛盾するかをツールが決めたり、既存の判断を統合・置換・編集したりはしません。

検索では既存の判断を先に示し、新しいメモは未確認と表示します。人が確認するまでは、現在のプロジェクト資料と確認済みの指示を優先します。

## 人が見直すための通知

別々の作業で同じ内容が繰り返し確認された場合、人に見直しを促すことがあります。ツールが採用を決めるものではありません。初期設定では次を目安にします。

- 種類にかかわらず、確認待ちのメモが4回以上別々に確認されたら、確認済みのメモとして採用するか見直す。
- 手順のメモが3回以上別々に確認されたら、再利用できるAIスキルにするか見直す。

回数だけでは採用しません。対象範囲、根拠、食い違い、現在のプロジェクト資料が変わっていないかを人が確認します。

## 保存前に非公開情報を守る

保存前に、入力そのものとデコード後の文字列を調べます。認証情報らしい内容、秘密鍵、authorizationの値、環境設定ファイルのパス、生のセッションID、telemetry IDが見つかった場合、内容を表示せず入力全体を拒否します。

確認待ちフォルダへの書き込みは、サイズと文字コードを制限し、既存ファイルを上書きしない方法で行います。シンボリックリンク、ハードリンク、上書きを使った攻撃も拒否します。実行回数などを任意で記録する場合は、メモのグラフ外に置き、作業本文を入れません。

## 作業終了時の結果マーカー

共通の指示書は、作業の最後に次のマーカーを1つ付けるようAIへ求める場合があります。

```text
<!-- brain-capture:v1 saved|duplicate|reinforced|none|error -->
```

マーカーを見れば、メモの保存結果が分かります。メモ本文には入りません。安全なstop hookは、マーカーがなければ同じAIへ一度だけ判断を促します。会話を読み取ったり、自分でメモを保存したりはしません。

接続時の範囲は[AIごとの接続方法](agent-integration.ja.md)、データの扱いは[プライバシーと公開前の確認](privacy.ja.md)を参照してください。
