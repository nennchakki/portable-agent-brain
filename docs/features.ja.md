## Hermes-Agentとの違い

Hermes Agentは、モデルを使って会話し、コマンド実行やファイル操作などを行うAIエージェントです。Portable Agent Brainは、そうしたAIから呼び出すメモの保存・検索ツールです。役割が違うので、併用する使い方もあります。[Hermesのツール一覧](https://hermes-agent.nousresearch.com/docs/user-guide/features/tools/)

Hermesにも記憶があります。「Hermesは毎回忘れるから必要」という説明ではありません。Hermes内で使うモデルを替えることと、別のAIアプリへ移ることは別です。モデル変更自体はHermesが対応しており、それだけで保存済みの知識を捨てる必要はありません。[モデルの切り替え](https://hermes-agent.nousresearch.com/docs/user-guide/configuring-models/)

| 比べるところ | Hermes Agent | Portable Agent Brain |
|---|---|---|
| 主な役割 | 会話し、道具を使って作業する | 複数のAIから使うメモの保存先と検索方法を用意する |
| 記憶 | 組み込みの `MEMORY.md` と `USER.md`、過去セッションの検索 | プロジェクト別のMarkdownメモを検索し、必要な部分を返す |
| 次の会話への引き継ぎ | 組み込みメモリはセッション開始時に読み込まれる | 共通の指示書を読んだAIが、必要なときに `brain context` を呼ぶ |
| 手順の再利用 | スキルの作成・更新に対応。スキルは共有もできる | 手順をメモとして保存する。実行用スキルへ自動変換はしない |
| 保存内容の確認 | メモリやスキルの書き込みを承認待ちにする設定がある | 保存コマンドは確認待ちのメモだけを扱い、自動承認しない |
| 外部メモリ | 外部メモリ提供元の追加に対応 | 自分のMarkdownフォルダを使う。Hermes用の専用メモリプラグインは未提供 |
| 図で見る | 学習履歴のグラフ表示がある | Obsidianでメモとリンクを表示する。専用の画面はない |

Hermes側の詳細は、[メモリと承認・グラフ表示](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory/)、[スキル](https://hermes-agent.nousresearch.com/docs/user-guide/features/skills/)、[外部メモリ](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory-providers/)を参照してください。機能の有無だけで優劣をつける比較ではありません。

このリポジトリを作った理由は、Hermesを使っていても結局ほかのAIを試し、そのたびに説明や蓄積をやり直すのがつらかったからです。残したいのは特定のAIの内部状態より、次のAIにも読んでほしい作業上の知識でした。

Hermesの中だけで困っていないなら、Portable Agent Brainを追加する必要はありません。複数のAIツールを行き来し、同じプロジェクトのメモを自分で管理したいときに使ってください。Hermesと併用する場合も、既存メモリを消したり、別のAIとHermesの保存フォルダ全体を共有したりする必要はありません。対応する設定ファイルから共通の指示書を参照する方法を確認し、[接続用プロンプト](../prompts/connect-agent.ja.md)で案内します。専用連携を実機で確認済みという意味ではありません。

比較は2026-09-05の公式説明と、このリポジトリの0.1.0実装に基づきます。利用中のHermesの版や設定によって使える機能は異なります。

## 9つのコマンド

コマンドは、ターミナルで実行する操作の名前です。AIに任せる場合は、名前を暗記せず「この作業に関係するメモを探して」と頼めます。

| コマンド | 何をするか | ファイルの変更 |
|---|---|---|
| `brain init` | 空のメモ用フォルダを用意する | 保存先と空のサブフォルダを作る |
| `brain setup` | 保存先、AIとの接続、任意のコマンド配置やGit設定を行う | 選んだ設定だけ変更する |
| `brain search` | 検索語に合うメモを一覧で探す | しない |
| `brain context` | プロジェクトと作業に合うメモの抜粋を、量を絞って返す | しない |
| `brain learn` | 書式を整えた1件のメモを、確認待ちとして保存する | 確認待ちのメモを作る |
| `brain learn-extract` | 短い作業要約からメモを作り、重複や追加の根拠を確認する | 確認待ちのメモを作成・更新する場合がある |
| `brain validate` | メモの形式、プロジェクト登録、リンクを検査する | しない |
| `brain release-check` | 公開するソフトに秘密情報などが混ざっていないか検査する | しない |
| `brain capture-hook` | AIが保存の要否を判断したか、結果マーカーを確かめる | しない。条件に応じてAIへの通知を返す |

このページの例は、ダウンロードしたソフトのフォルダ内で `./brain` を使います。コマンドとしてインストール済みなら `brain` でも呼べます。`./brain --help` で一覧、`./brain context --help` のように指定すると各操作の全引数、`./brain --version` で版を確認できます。

## 保存先とAIの接続

`init` は入れ物だけを用意します。`setup` で接続するAIを選んだ場合は、そのAIが読む設定ファイルに共通の指示書 `adapters/external-brain.md` への参照も追加します。「ゲートウェイ」と呼んでいた共通の入口は、この指示書です。通信を中継するサーバーではありません。

Claude CodeとCodexには専用の指定があります。`generic` は、指定した `AGENTS.md` を読むAI向けです。すべてのAIへ自動で接続する指定ではありません。既存設定を残してバックアップを作り、同じ参照の二重追加を避けます。

| 設定したいこと | 主な引数 |
|---|---|
| 保存先 | `--library`（別名 `--root`） |
| 接続するAIと設定ファイル | `--agent`、`--claude-file`、`--codex-file`、`--generic-agents-file` |
| 共通指示書や別の実行環境 | `--adapter`、`--agent-home` |
| Codexの優先設定を明示的に選ぶ | `--codex-override` |
| コマンドを配置する場所と方法 | `--install-command-dir`、`--cli-method auto\|symlink\|wrapper` |
| 質問を表示せず、指定値で実行 | `--non-interactive`。必要な値はAIが確認してから渡す |
| 今回の保存先を既定値として記録しない | `--no-save-default` |

保存先は `--library` → 環境変数 `BRAIN_LIBRARY` → setupで保存した設定 → `~/agent-library` の順で決まります。環境変数は、実行中のプログラムへ値を渡す仕組みです。設定ファイルの場所は `BRAIN_CONFIG` や `XDG_CONFIG_HOME` でも変更できます。[設定の詳細](getting-started.ja.md)

ソフト本体とメモの保存先は分けてください。別のAIから使うときは、同じ保存先がそのAIにも見えるか確認します。コマンドの配置だけでは、どこからでも見つかるようにするPATH設定は変わりません。通常のsetupはモデル、権限、既存hooksを変更しません。[接続と解除](agent-integration.ja.md)・[隔離された実行環境](sandbox.ja.md)

## メモを探す・作業に必要な部分を読む

`search` は「候補を一覧で見たい」ときに使います。タイトル、場所、状態、一致した理由を返します。`--project` を指定すると、そのプロジェクトのメモだけを検索します。共通のメモも一緒に見たい場合は、プロジェクト指定なしの検索か `context` を使います。

`context` は「これから行う作業のために読ませたい」ときの操作です。対象プロジェクトと共通のメモから選び、リンク先も調べて、重複する抜粋を除いて返します。どの資料を優先するか、なぜ選んだか、確認待ちかどうかも示します。

次の2行は、同梱の架空プロジェクトを読むだけです。自分の履歴やメモには触れません。`$PWD` は、今いるソフトのフォルダを表します。

```sh
./brain search --library "$PWD/examples/demo-project" "cache expiry"
./brain context --library "$PWD/examples/demo-project" --project sample-weather-cli --task-type debugging "stale cached output"
```

| 調整するもの | 指定方法と既定値 |
|---|---|
| 検索の件数 | searchの `--limit`。既定5件、1〜50件 |
| 抜粋の文字数と件数 | contextの `--max-chars` は既定12,000文字、`--max-items` は12件。作業の種類によって、さらに小さい目安を適用する |
| リンクを何段たどるか | `--hops 1` または `2`。既定1段 |
| 選ぶための点数 | `--min-score`。既定600。正しさの確率ではない |
| 話題を説明するメモの本文 | `--include-concepts`。通常は本文を省く |
| 作業の種類 | `--task-type`。contextでは省略時に検索語などから推定する |
| 選ばれなかった理由も調べる | `--trace`。診断情報は通常の結果とは別の出力先に出す |
| 古い、置き換え済みのメモ | `--include-superseded`。通常は除外する |
| AIや別プログラム向けの出力 | `--json`。項目名と値の形式で返す |

作業の種類は `architecture`（設計）、`implementation`（実装）、`ui`（画面）、`debugging`（不具合調査）、`testing`（テスト）、`build`（ビルド）、`documentation`（文書）、`research`（調査）、`analysis`（分析）、`data`（データ）、`security`（安全性確認）の11種類です。単純な誤字修正などではcontextを省略する結果になることもあります。

検索は、語の一致と小さな日英の語彙対応を使います。文章の意味を数値化するベクトル検索や、AIによる検索結果の再評価は搭載していません。「AIへ渡す本文を絞る」仕組みであり、ディスク上でも選ばれた数ファイルしか読まないという意味ではありません。候補を探す過程では対象のメモ本文を走査します。

## プロジェクト・メモの種類・リンク

プロジェクト登録は `projects/<slug>/<slug>.md` と、その隣の `project.yaml` を作って行います。`slug` は短い識別名です。専用の登録コマンドはないため、[入門ガイドの依頼文](guide.ja.md)でAIに任せられます。見本は `templates/project/` にあります。

設定の `always_include` は毎回の候補、`task_include` は特定の作業で読む候補を指定します。ただし出力上限は適用され、省いた場合はその件数を報告します。`search_include` は現在、設定として読み込むだけで、検索範囲を制限する機能は未実装です。秘密のメモを検索から隠す目的には使わないでください。

メモの種類は、用途を表します。名前だけで正しさや優先度は決まりません。

| 用途 | ファイル内の種類名 |
|---|---|
| プロジェクトの概要・決まり | `project-knowledge`、`project-rule` |
| 全体の方針・共通手順 | `principle`、`protocol` |
| 失敗などから学んだこと・判断の理由 | `lesson`、`decision` |
| 事実・好み・制約・手順 | `fact`、`preference`、`constraint`、`procedure` |
| 話題・資料・プロフィール・スキルの説明 | `concept`、`reference`、`profile`、`skill` |

リンクは「関連する」「この失敗を防ぐ」「この判断を置き換える」などの関係を表せます。実際の項目名は `project`、`domains`、`related`、`uses`、`depends_on`、`implements`、`prevents`、`caused_by`、`conflicts_with`、`supersedes`、`superseded_by` です。存在するメモへ、内容に根拠のあるリンクだけを付けます。詳しい意味と書式は[メモの形式](knowledge-model.ja.md)にあります。

現在のプロジェクト資料が変わっていれば、古いメモより現在の資料を確かめます。メモ内では、確認済みの指示、根拠を確認した情報、観察した情報、確認待ちの順で扱います。リンクがあるだけで承認済みにはなりません。却下されたメモは通常の作業用の検索から外れます。

## メモを作る・重複や矛盾を確認する

普段の作業後には `learn-extract` を使います。AIが作った短いJSON要約を読み、事実・好み・制約・教訓・手順・判断案の6種類からメモを作ります。コマンド自身がAIを呼び出すわけでも、会話ファイルを要約するわけでもありません。

入力にはプロジェクトと作業の種類が必要で、JSONとコマンド側の指定を一致させます。`shared` は、複数のプロジェクトにそのまま使える知識だけに使います。どのプロジェクトの話か不明な内容を、とりあえず入れる場所ではありません。

次の例は架空の作業要約を使った練習です。`--dry-run` があるため、保存しません。

```sh
./brain learn-extract --library "$PWD/examples/demo-project" --project sample-weather-cli --task-type debugging --dry-run --json examples/demo-project/task-summary.json
```

本当に保存するときは、自分の保存先、登録済みプロジェクト、自分の短い要約を指定します。公開ソフトの中には書き込めません。秘密情報や会話の原文を使わず、まず保存しない検査を行ってから `--dry-run` を外します。入力はファイルか `--stdin` のどちらかで渡し、最大65,536バイトです。[JSONの例と保存方法](automatic-capture.ja.md)

保存先は `inbox/candidates/`。新しいメモは人が確認する前の情報です。同じ内容の再送はファイルを増やさず、独立した別の作業でも確認できたと判断した場合は根拠の回数などを更新します。同じ要約の繰り返しで確認回数を増やす仕組みではありません。

`learn` は、すでに書式を整えた1件のメモJSONを渡す、より直接的な操作です。重複や関連メモを提案しますが、`learn-extract` と同じ自動の重複抑制はしません。通常の作業後の保存には `learn-extract` を選んでください。

自分でメモJSONを用意する場合、`learn` は上の6種類に加えて、共通手順の `protocol` と保存不要を示す `none` も受け付けます。`--project` は任意で、`--dry-run` による保存前の確認も使えます。

矛盾しそうな判断は警告とリンクで示し、人に確認を求めます。自然言語の意味を完全に判定するものではありません。繰り返し確認された教訓や手順から、指示やスキルとして見直す提案が出ることはありますが、確認回数だけで自動採用しません。保存0件も正常な結果です。

## Obsidianと形式の検査

Obsidianでは自分のメモのフォルダを開きます。Markdownの本文とリンクをそのまま使えるので、Portable Agent Brain用の追加プラグインは必須ではありません。[画面での開き方と画像](guide.ja.md#8-obsidianではメモの保存フォルダを開く)

`validate` は、プロジェクト登録、IDの重複、リンク先、置き換え関係の循環などを検査します。孤立したメモには警告が出ることがあります。JSONにはグラフの件数や関係も含まれます。付属の例で試すなら次を実行します。

```sh
./brain validate --library "$PWD/examples/demo-project" --json
```

確認待ちのメモやテンプレートは、validateが数えるメモ（ノード）に含まれません。Obsidianでは表示される場合があるため、両者の数は一致しないことがあります。`brain graph` というコマンドや、専用のグラフ画面はありません。

検査の成功は「メモに書いた内容が正しい」という保証ではありません。外部のWebリンクに接続して生存確認する検査でもありません。書式の定義は `schemas/`、空の書式見本は `templates/`、架空の実例は `examples/demo-project/` にあります。

## Git・保存忘れの通知・公開前チェック

### Gitの接続と明示的な送信

| `setup --git-mode` | 何をするか |
|---|---|
| `none` | Git設定を変更しない。既存の同期を止める意味ではない |
| `local` | 必要ならローカルのGit管理を始める。既存の送信先は残す |
| `existing` | メモのフォルダ自体が、すでにGit管理の単位になっていることを確認する |
| `remote` | 既存GitHubのprivateと書き込み権限を検証し、必要ならGit管理を始めて `--remote-url` を登録する。名前は `--remote-name`（既定 `origin`） |

いずれも自動のcommit、pull、pushやGitHub上のリポジトリ作成は行いません。`remote` はGitHub CLIによる認証と、github.comのprivateへのHTTPS接続を必要とします。Git設定が途中で失敗した場合は状態を残し、Git履歴を削除しません。

`brain github connect` でprivateの接続先を登録し、`status` で再確認できます。`brain github push` は送信履歴のプレビュー、`--approve` を付けた操作が再検証後の明示送信です。[private GitHubへの保存](github-sync.ja.md)を参照してください。

### 保存の判断を促す通知

`capture-hook` は、AIの返答に `brain-capture:v1` の結果マーカーがあるかを確認します。なければ条件に応じて、同じAIへ保存の要否を判断するよう促します。会話を保存したり、別のAIを起動したりする処理ではありません。

結果は `saved`（保存）、`duplicate`（重複）、`reinforced`（根拠の追加）、`none`（保存不要）、`error`（失敗）です。マーカーを検出しても、実際に保存できたかまでは検証しません。不正な入力や再通知中などは、終了を妨げず通します。通常のsetupではhookを自動で設置しません。[接続上の注意](agent-integration.ja.md)

### 公開ソフトを変更する人向けの検査

`release-check` は、この公開リポジトリの作業中のファイル、到達可能なGit履歴、送信先などを調べます。個人のメモ置き場を日常的に検査するコマンドは `validate` です。

```sh
./brain release-check --json
```

`--root` で公開ソフトの場所、`--denylist` で公開してはいけない語の一覧を追加指定できます。その一覧は公開フォルダの外に置きます。未知の画像などのバイナリや大きなファイルは拒否しますが、READMEの画像は、画像と付随情報を確認した同一ファイルだけを警告付きで許可しています。画像内の個人情報を自動で読んで判断する検査ではありません。

保存時と公開前に秘密情報のパターン検査がありますが、すべての個人情報を検出できるわけではありません。クラウド型AIに読ませた文章は、そのサービスで処理される可能性があります。「ローカル保存」と「外部へ一切送らない」は別です。[プライバシーと検査範囲](privacy.ja.md)

## 今はできないこと

履歴ファイルを直接読み取る専用インポーター、定期同期、独自のチャット画面、モデルの学習、メモの自動承認はありません。`--history-source` も、存在するパスを確かめて手順を表示するだけです。READMEのプロンプトでは、利用を許可した履歴をAIが読んで要約し、保存コマンドへ渡します。

プロジェクト登録、メモの承認・削除、実行用スキルへの変換は、それぞれ専用CLIがありません。AIに依頼する場合も、変更内容を確認してから行います。設定を書き換えられないAIや、別の場所にあるメモを読めないAIが、プロンプトだけで操作可能になるわけではありません。

最初は1つのプロジェクトで、次にも使いたいメモを1件残せれば十分です。操作で困ったら[入門ガイドのエラー対処](guide.ja.md#11-エラーが出たら削除や権限変更の前に確認する)、言葉がわからなければ[用語集](guide.ja.md#12-わからない言葉を引く)へ。解決しない場合は秘密情報を除いて[Issues](https://github.com/nennchakki/portable-agent-brain/issues)へどうぞ。
